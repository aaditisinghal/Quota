# Quota × HR clone — Autonomous Onboarding, Payouts and Close (for Claude Code)

This extends Quota; it is not a second product. It adds:
1. A **computer-use agent** that onboards the company from its HR system and writes results back, with every step verified through the system's API.
2. **Learning:** the agent's first run becomes a replayable playbook.
3. **Split payouts:** Stripe Connect for partners and agents, the payroll file for employees.
4. **Receipt reconciliation**, with Elastic doing the extraction and matching.
5. A **next-quarter incentive budget** from margin and rep metrics.
6. An **API contract plus an MCP server**.
7. One **"close the day" run** that ends with "finance sorted".

Two folders:
- `C:\Users\aadit\Downloads\Quota` (Quota, Python)
- `C:\Users\aadit\Downloads\bamboohr-clone` (the HR clone, Bun and React). Edit it freely.

## Rules

- Same as NEXT_TASKS.md: after each task run tests, commit `C<n>: <title>`, and continue. Never ask; log choices in `ASSUMPTIONS.md`. Keys stay in `.env`, never in code or chat.
- **Verified by API, always.** Every agent action (read or write) is checked against the clone's API (`/__clone/state`, `/__clone/diff`, `/__clone/ledger`) or Stripe's API. A step that can't be verified counts as failed.
- **Demo never depends on the network.** Record the Claude-driven runs; replay them in the viewer; run playbooks live, since they make no model calls.
- **Label anything simulated.** Rep metrics (CSAT, pipeline, cycle time, CAC) are generated by Quota's CRM simulator and labeled simulated in the UI and README.

## C3 — The computer-use agent (Session A)

`quota/cua/`:
- `browser.py`: Playwright Chromium, viewport 1280×800, opens `CLONE_URL`. Provides `screenshot() -> png`, `do(action) -> result` mapping toolset members to Playwright:
  - `left_click`, `double_click` → `page.mouse.click` at the scaled coordinates
  - `type` → `page.keyboard.type`
  - `key` → `page.keyboard.press` (map xdotool-style names: `Return` to `Enter`, `ctrl+a` to `Control+A`)
  - `scroll` → `page.mouse.wheel`
  - `wait` → `asyncio.sleep`
  - `zoom` → crop and return the region
- `agent.py`: the loop.
  - `messages.create(model=QUOTA_CUA_MODEL, tools=[{"type": "computer_toolset_20260801"}, REPORT_TOOL, DONE_TOOL], …)` → execute each computer `tool_use` → return a tool result with a fresh screenshot → repeat until `done` or the step budget (120) is reached.
  - Two custom tools sit next to the toolset:
    - `report_records(records: [...])`: the agent hands over what it read (people, compensation and commission rows) as JSON
    - `done(summary)`
- `recorder.py`: every step appends to `runs/cua/<run_id>/trajectory.jsonl`:
  `{step, ts, mode: "model"|"playbook", action, coordinate, text, url, screenshot: "step-0007.png", element: {role, name, selector, bbox}, model_calls, input_tokens, output_tokens}`.
  - `element` comes from `document.elementFromPoint` at the coordinate (role, accessible name, a stable CSS selector, bounding box) and feeds the playbook (C4).
  - The recorder also publishes each step to an in-process event bus for the live viewer (C5).

**Two tasks.** Prompts live in `quota/cua/tasks/*.md` and are plain-language instructions an HR admin would understand.
1. **`onboard_sales`:** "Open People. Show the Sales, Sales Operations, Finance and Partners departments. For each person, open their profile, go to the Job tab, and read their job title, manager, compensation (pay rate, pay type, effective date) and every commission row. Report everything with `report_records`. Do not change anything."
2. **`record_commissions(payout_file)`:** "For each line in this payout file, open the employee, go to Job → Commission, add an entry with this date, amount and comment, and save. Do not change anything else."

**Verification** (`quota/cua/verify.py`):
- **Read tasks:** compare `report_records` field by field with C2's API snapshot. Output: `CUA read 28 people, 156 fields; 156/156 match the HR API`.
- **Write tasks:** `/__clone/diff` must contain exactly the expected commission rows (employee, date, amount, comment) and **nothing else**. `/__clone/ledger` must show each action with actor Jerry and outcome ok.
- Any extra diff counts as a failure; report it as such.
- Feed the result into Quota: the onboarding snapshot loads with `source = "bamboohr:cua"`, and the write-back records `hr_writeback` facts that link each commission line to the clone ledger seq.

**Done when:** both tasks complete live once with Sonnet and verify 100%. Commit the recorded runs from `runs/cua/` (screenshots plus jsonl) to `demo/cua-runs/` so the viewer works offline.

## C4 — Learn the job: compile a run into a playbook (Session A)

The agent's first run is expensive; its second shouldn't be.

- `quota/cua/compile.py`: from a successful, verified model run, build `playbooks/<task>.json`.
  - Each step: `{action, locator: {role, name} | {selector}, value_from: "record.field"|literal, expect: {url_contains | text_visible}}`.
  - Per-person loops are generalized by detecting the repeated pattern (open profile → Job tab → table) and parameterizing the employee id in the URL (`/employees/employee.php?id={id}&page=…`, or whatever the clone uses).
- `quota/cua/playbook.py`: runs a playbook with Playwright locators and **no model calls**, emitting the same trajectory events. The pointer position is each element's bounding-box center, so the viewer looks identical.
  - **Self-heal:** if a locator fails or an `expect` doesn't hold, hand that one step to the model with the current screenshot, record the fix, update the playbook (version +1) and continue.
- **Metrics** for both modes go to `out/cua_metrics.json`: steps, wall time, model calls, tokens, estimated cost (from the response `usage`), verification result.
  - Example line (the numbers must be measured): `onboard_sales: model run 4m12s, 61 model calls, $X | playbook 38s, 0 model calls | both 156/156 verified`.
- **"Practiced on a replica" story:** the clone resets deterministically, so `python -m quota cua train onboard_sales --runs 3` resets, runs the model, verifies, compiles, then runs the playbook twice on fresh resets and reports the pass rate. That's how this would onboard a real company: practice on a replica of their HR app, then run the playbook against the real one.

**Done when:** the playbook replays both tasks on a fresh reset with 0 model calls and 100% verification, and a deliberately renamed button in the clone gets self-healed with one model call.

## C7 — Receipts: upload, extract with Elastic, reconcile (Session B)

**The receipts that matter** after a payout:
1. The **payroll provider's register** (PDF) showing gross commission per employee.
2. **Bank or wire confirmations** (often phone photos or scans) for agents paid outside Stripe.
3. **Stripe transfer receipts**, already known through the API.

**Generate test receipts:** `python -m quota gen-receipts --period 2026-05` writes `inbox/receipts/`:
- `payroll_register_2026-05.pdf` (fpdf2, a realistic layout). **Plant one error:** Jordan paid $12,340.00 against an approved $12,000.00.
- `wire_confirmation_ana_ruiz.png`: a rendered image of a bank confirmation (PIL); amount, beneficiary, reference.

**Upload:** `POST /api/receipts` (multipart; principals with role Finance or Payroll). The UI gets a drop zone on Today + Ledger health: "Upload payout receipts".

**Extraction:**
- **PDFs:** an Elastic ingest pipeline `quota-receipts-attach` with the `attachment` processor (`field: data`, `target_field: attachment`, `remove_binary: true`). Index into `quota-receipts` (`text` plus `content: semantic_text`, `file_name`, `sha256`, `uploaded_by`, `kind`).
  - If Serverless rejects the attachment processor, extract with `pypdf` locally and index the text. Log which path was used and show it on the receipt card.
- **Images:** Claude Sonnet vision transcribes the receipt to text, then it's indexed the same way. The attachment processor isn't documented to OCR images.
- **Line parsing:** model with structured output `{payee, amount_cents, date, reference}`, plus the **verbatim guard** (each amount and name must appear in the extracted text).

**Reconcile** each parsed line against approved payout lines and Connect transfers (same period, payee matched by name or email, amount exact):
- `matched`, `amount_mismatch` (hold, escalate to the Controller, invariant INV6-style), `missing_on_receipt`, or `unexpected_payee`.
- Expected: Jordan +$340.00 is flagged; everything else matches.

**Elastic extras:**
- Add `quota_receipts_search` to the auditor agent's tools (ELASTIC_TASKS E6).
- The receipt card shows "found by: semantic search on 'payout confirmation for Ana Ruiz'" when the payee's name differs between systems ("A. Ruiz" vs "Ana Ruiz").

## C8 — Next-quarter incentive budget (Session B)

A dynamic incentive that's affordable by construction and becomes real only when signed.

**Metrics** (simulated in Quota's CRM, labeled). Per rep, per quarter:
- pipeline $
- win rate
- median sales-cycle days
- CSAT of their accounts (1–5)
- CAC (sales and marketing cost allocated per new customer)
- average discount
- clawback rate
- new ARR

Generate them in `sim/generator.py` with realistic correlations: fast cycles mean higher CSAT, heavy discounting means higher clawbacks.

**Budget** (`quota/incentives/budget.py`). Show every term in the UI as a waterfall:
```
gross_margin    = revenue - COGS                                (from the ledger + a COGS assumption in config)
target_op_margin= config (e.g. 15%)
incentive_room  = gross_margin - opex_ex_commissions - target_op_margin * revenue
pool            = min(incentive_room, payout_ratio_cap * projected_new_ARR)   # e.g. cap 12%
constraint      : blended CAC payback (CAC / (ARPA * gross_margin%)) <= 18 months after the pool
```

**Allocation** (`quota/incentives/allocate.py`):
- Score each rep with a weighted z-score over the metrics (weights in config; CSAT and cycle time weigh in alongside revenue, so cheap fast happy deals win).
- Estimate the marginal new ARR per incentive dollar per rep segment from the two simulated quarters (a simple linear fit, its R² shown).
- Allocate the pool greedily to the highest marginal-profit segments until marginal ROI < 1.0 or the pool is used up.
- **Output is a proposal**, not a payout:
  - per-rep or per-segment accelerators and SPIFs (e.g. "multi-year deals with CSAT ≥ 4.5: 1.2× accelerator")
  - expected profit impact
  - the CAC payback after

**Approval:**
- The proposal routes to the VP Sales Ops and the Controller, using existing approval routing with limits.
- Once both approve, Quota generates plan amendment v4 documents (YAML plus PDF) for each affected rep, to sign.
- Signed v4 becomes the plan in force on 2026-07-01. Quota never applies it to deals already booked.

**UI:** an **Incentives** tab with:
- the waterfall (revenue → gross margin → target margin → pool)
- the rep table (metrics, score, proposed multiplier, expected ARR)
- an "Approve proposal" button for Marcus and Priya
- the generated amendment previews

**Done when:** the proposal is reproducible from seed 7, satisfies the payback constraint, and approval produces v4 plan files.
